# ADR Skill — Usage Guide

How to use the **adr** skill to manage Architecture Decision Records (ADRs) through the whole workflow. The skill is invoked as `/adr <subcommand>` and drives the [adr-tools](https://github.com/npryce/adr-tools) CLI (installed at `/home/slavko/dotfiles/adr`).

An ADR is a short document that captures a single significant decision — what was decided, why, and the consequences. The skill uses the CLI to manage files (numbering, filenames, status links, index) so the agent never hand-creates or edits ADR files directly (except filling in the draft that `adr new` produces).

## Prerequisites

- The `adr` CLI is on `PATH` (`adr` → `/home/slavko/dotfiles/adr/adr`).
- The `adr-tools` skill is enabled (`default_skills.yaml`).

## Command Reference

| Subcommand | Underlying CLI | Description |
|---|---|---|
| `/adr init [dir]` | `adr init` | Initialize an ADR repo (default `doc/adr`) |
| `/adr new "Title"` | `adr new` | Create a new numbered ADR |
| `/adr new -s N "Title"` | `adr new -s N` | Create an ADR that supersedes ADR N |
| `/adr new -l T:L:R "Title"` | `adr new -l` | Create an ADR linked to an existing one |
| `/adr link S L T R` | `adr link` | Link two existing ADRs |
| `/adr list` | `adr list` | List all ADRs |
| `/adr generate toc` | `adr generate toc` | Generate a markdown table of contents |
| `/adr generate graph` | `adr generate graph` | Generate a Graphviz dependency graph |
| `/adr help [cmd]` | `adr help` | Show usage |

## Workflow

### 1. Initialize (first time only)

```text
/adr init
```

Creates `doc/adr/` and seeds the first record `0001-record-architecture-decisions.md`. Use a custom directory to keep ADRs elsewhere:

```text
/adr init doc/architecture/decisions
```

This writes a `.adr-dir` file so later commands find the directory automatically.

### 2. Create a new ADR

```text
/adr new "Use PostgreSQL for the primary datastore"
```

The skill numbers it (next available, zero-padded `NNNN`), slugifies the title into `NNNN-use-postgresql-for-the-primary-datastore.md`, fills the template with `Status: Accepted`, and opens it for editing. Fill in **Context**, **Decision**, and **Consequences** — including rejected alternatives and trade-offs.

### 3. Supersede a decision

Never edit an accepted ADR. Record the change as a new ADR that supersedes the old one:

```text
/adr new -s 2 "Migrate from MongoDB to PostgreSQL"
```

This writes `Supercedes [title](file)` into the new ADR and `Superceded by [title](file)` into ADR 2, removing its `Accepted` status.

### 4. Link decisions

Link two existing ADRs with a relationship label:

```text
/adr link 4 Amends 2 "Amended by"
/adr link 7 "Depends on" 3 "Required by"
```

Or link at creation time:

```text
/adr new -l "2:Depends on:Enables" "Add connection pooling"
```

### 5. List ADRs

```text
/adr list
```

### 6. Generate index and graph

```text
/adr generate toc
/adr generate graph | dot -Tsvg > graph.svg
```

## ADR File Format

Generated by the skill from the template:

```markdown
# NUMBER. TITLE

Date: YYYY-MM-DD

## Status

Accepted

## Context

The issue motivating this decision, and any context that influences or constrains the decision.

## Decision

The change that we're proposing or have agreed to implement.

## Consequences

What becomes easier or more difficult to do and any risks introduced by the change that will need to be mitigated.
```

## Rules of Thumb

- **One decision per ADR**, kept short (readable in ~2 minutes).
- **Record the why** — rationale and rejected alternatives matter more than the what.
- **Never edit an accepted ADR** — supersede it with `/adr new -s N`.
- **Only the CLI creates files** — never hand-create a `NNNN-title.md` or edit `.adr-dir`.
- **Use present tense** — "We use X", not "We will use X".
